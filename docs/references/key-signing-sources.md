# Key and Signing Source Record

Retrieved 2026-08-27 for the non-custodial signer architecture. These sources are evidence only; they do not authorize any key generation, wallet connection, signature, broadcast, or deployment.

| Source | Verified behavior used by the architecture |
| --- | --- |
| [Solana: Signing in Production](https://solana.com/docs/core/transactions/signing-in-production) | A transaction needs valid signatures from required signers. Solana distinguishes local keypairs from end-user browser wallets, KMS/HSM, and managed/MPC approaches, and warns against embedding or committing private keys. The design uses a user-controlled signer for user assets and reserves KMS/HSM discussion for separately authorized service-owned keys only. |
| [Solana: Create a Keypair](https://solana.com/developers/cookbook/wallets/create-keypair) | Wallet applications may manage user keypairs; raw keypairs hold private material and should not be embedded or committed. The bot will never generate or handle such material. |
| [Solana: Transaction Structure](https://solana.com/docs/core/transactions/transaction-structure) | A transaction contains signatures and a message. Signatures are 64-byte Ed25519 signatures over the serialized message. The message includes signer/account permissions, a recent blockhash, and instructions. A recent blockhash expires after 150 slots unless a durable nonce is used. Native SOL transfers can target any account, so recipient verification is a user-safety requirement. |
| [Solana: simulateTransaction](https://solana.com/docs/rpc/http/simulatetransaction) | Simulation evaluates a transaction without broadcasting it. The architecture uses a fresh pre-sign simulation where feasible and treats simulation as an advisory preflight rather than settlement proof. |
| [Solana: sendTransaction](https://solana.com/docs/rpc/http/sendtransaction) | Submission relays a signed client transaction unchanged and returns before the cluster confirms it. The architecture keeps submitted, confirming, confirmed, failed, and unknown states separate. |
| [Solana Mobile: Mobile Wallet Adapter](https://docs.solanamobile.com/developers/mobile-wallet-adapter) | MWA connects dApps to mobile wallet apps for Solana signing. The source lists Android / Android Chrome support and no current iOS, Safari, Firefox, Opera, or Brave support. The architecture therefore treats MWA as one optional Android transport, not universal mobile signer support. |
| [Sign In With Solana specification](https://github.com/phantom/sign-in-with-solana) | SIWS standardizes wallet-ownership authentication with domain, address, nonce, issuance/expiration time, and request ID fields; the returned signature/message should be verified server-side against the original request. The architecture uses a one-time, audience-bound wallet-control challenge only for authorization—not as a transaction approval. |
| [Android Keystore system](https://developer.android.com/privacy-and-security/keystore) | Android Keystore keys are designed to remain non-exportable and may be backed by secure hardware where the device supports it. It can constrain key use and require user authentication. The architecture uses it, when verified on-device, to protect an encryption/wrapping key—not to claim a universal hardware-backed Solana Ed25519 signer. |
| [Apple: Protecting keys with Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave) | Apple states that the Secure Enclave is isolated from the main processor and does not expose plaintext of keys generated there, but its documented key support is NIST P-256. The architecture does not claim it can directly hold a Solana Ed25519 key; native iOS requires a separately validated wrapper/envelope design or external signer. |
| [Apple: Keychain services](https://developer.apple.com/documentation/security/keychain-services) | Keychain services provide an encrypted database for small confidential data scoped to an app and its access policy. The architecture uses it as native protected storage for an encrypted Solana seed/key envelope where appropriate, not as automatic cross-device recovery. |
| [MDN: CryptoKey extractable](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey/extractable) | Browser Web Crypto keys can be marked non-extractable and require a secure context, but this property only controls Web Crypto export operations. The architecture treats it as a key-encryption control, not proof of hardware isolation or protection from a compromised browser process. |

## Source limitation

The confirmation-guide URL returned no extractable content during this retrieval. The architecture relies instead on the available official `sendTransaction`, `simulateTransaction`, and transaction-structure documentation for the required submission/finality distinctions. A future implementation must re-check the current confirmation API and commitment guidance before calling any RPC method.
