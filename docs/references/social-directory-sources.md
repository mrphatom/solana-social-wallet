# Social Tipping Directory Source Record

Retrieved 2026-08-27 for the decentralized Discord/Telegram identity-to-Solana directory design. The records below are source evidence only; they do not authorize a live directory, platform API connection, identity attestation, chain write, signing request, or transfer.

| Source | Verified behavior used by the architecture |
| --- | --- |
| [Discord: User Resource](https://docs.discord.com/developers/resources/user) | A Discord user object has a stable `id`, while its `username` is explicitly not unique across the platform. The directory uses a provider-verified user ID as the attestation subject and treats usernames/nicknames/display names as non-authoritative discovery labels. |
| [Telegram: Bot API User](https://core.telegram.org/bots/api#user) | Telegram Bot API updates carry a `User` object and `update_id`; the API documents deduplication/ordering considerations for update IDs and webhook retry behavior. The directory relies on a verified platform event to obtain a subject ID and requires adapter replay controls. |
| [Solana: Accounts](https://solana.com/docs/core/accounts) | Solana accounts are keyed by 32-byte addresses and only the owner program can modify an account's data. The design treats an optional on-chain registry as a program-owned immutable/revocable attestation log, not a mutable operator database. |
| [Solana: Program Derived Addresses](https://solana.com/docs/core/pda) | PDAs are deterministically derived from a program ID and seeds, have no private key, and the deriving program can authorize them via `invoke_signed`. The design uses namespaced, non-user-controlled hash commitments as proposed registry indexing material, never as a user wallet or payment authority. |
| [W3C: Verifiable Credentials Data Model v2.0](https://www.w3.org/TR/vc-data-model-2.0/) | W3C defines issuer, holder, subject, verifier, and verifiable-data-registry roles and emphasizes that a verifiable credential's authenticity/currency does not by itself make a claim suitable to rely on. The directory adopts these roles but defines its own narrow social-address attestation instead of claiming generic VC interoperability. |
| [W3C: Decentralized Identifiers v1.1](https://www.w3.org/TR/did-1.1/) | DIDs are controller-managed identifiers that can be resolved using a verifiable data registry. The specification is method-agnostic. The design uses DID/VC concepts only as vocabulary and does not invent or claim a deployed DID method. |
| [RFC 8785: JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785) | Cryptographic signing requires an invariant byte representation. JCS defines canonical JSON through I-JSON constraints, deterministic object-property sorting, and UTF-8 output. The proposed off-chain attestation envelope uses a named canonicalization version and string encodings for integer values; every verifier must parse, validate, canonicalize, then verify or abort. |

## Source limitation

These platform documents establish that platform IDs are preferable to Discord usernames and describe the Solana account/PDA model. The W3C/RFC sources provide general credential, decentralized-identifier, and deterministic-serialization concepts. None defines a universal public protocol for Discord/Telegram identity attestations or a decentralized social-payment directory. The attestation format, governance, node membership, privacy retention, and chain anchor remain product decisions requiring a separate specification, independent review, platform-policy review, and explicit authorization before implementation.
